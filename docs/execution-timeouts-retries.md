# 실행 시간 제한과 준비 단계 재시도

## 처리 흐름

1. 요청 내용과 `requestId`로 실행 ID를 만든다. 저장된 완료 결과가 있으면 반환한다.
2. Sandbox 서버의 실행 잠금을 확보한다. 실행 중 요청이 들어오면 HTTP 409와 `Retry-After`를 반환한다.
3. 이전 프로세스가 남긴 자원을 회수한다. 회수가 끝나지 않으면 HTTP 503으로 새 작업을 보류한다.
4. 시도마다 새 작업 폴더·namespace·이미지를 사용해 준비와 검증을 수행한다.
5. 일시적인 의존성 다운로드 오류는 설치 단계의 남은 시간 안에서 재시도한다.
6. 준비 단계가 시간 초과되면 자원 정리를 확인하고, 허용된 경우 제한시간을 늘려 한 번 더 실행한다.
7. 시도 이력과 최종 결과를 저장한다. 같은 요청을 다시 보내면 이 결과를 반환한다.

## 요청 옵션

| 필드 | 기본값 | 의미 |
| --- | --- | --- |
| `deadlineSeconds` | 기존 선택 필드 | 요청 전체의 누적 시간 상한. 60~7200초. 준비 재시도에는 필수 |
| `preparationTimeoutSeconds` | 1200초 | 한 시도의 clone·검사·이미지 빌드·배포 준비 상한 |
| `phaseTimeouts` | 단계당 600초 | 단계별 상한을 지정하는 객체 |
| `retryDownloads` | false | 설치 단계의 일시적인 다운로드 오류 재시도 |
| `maxPreparationRetries` | 0 | 준비 단계 전체 재시도 횟수. 현재 0 또는 1 |

`phaseTimeouts`는 `clone`, `install`, `build`, `test`, `image_build`, `image_load`, `rollout`을 받는다. 각 값은 1~7200초 정수다. 실제 실행에는 단계 상한, 준비 상한, 전체 남은 시간 중 가장 짧은 제한을 적용한다. 이미지 로드에 명시적인 제한이 적용되며, 외부 명령의 시작과 종료 처리에도 시간이 필요하다.

하위 도구의 자체 제한도 함께 적용된다. 예를 들어 배포 스크립트의 kubectl rollout 기본 대기는 240초다. `phaseTimeouts.rollout`은 이를 감싸는 프로세스의 상한이며, 더 큰 값만 지정해서 kubectl 자체 대기를 늘리지는 않는다. 배포 기동 실패의 정책 변경은 별도 검토 범위다.

전체 상한에서 기존 90초를 정리에 확보한다. 정상적인 준비 프로세스에는 이 범위 안에서 최대 30초의 정리 여유를 주고, 남은 시간으로 부모 프로세스가 잔여 자원을 회수한다. `deadlineSeconds`가 90초 이하이면 실제 작업에 사용할 시간이 없을 수 있다.

아래 JSON은 Sandbox API 직접 호출 예시다. Windows·Mac·Linux에서 동일한 필드를 사용한다.

```json
{
  "repositoryUrl": "https://github.com/example/project.git",
  "branch": "main",
  "requestId": "validation-unique-id",
  "chaosMode": "suite_standard",
  "deadlineSeconds": 3570,
  "preparationTimeoutSeconds": 1200,
  "phaseTimeouts": {
    "install": 600,
    "build": 600,
    "test": 600,
    "image_build": 600,
    "image_load": 600,
    "rollout": 600
  },
  "retryDownloads": true,
  "maxPreparationRetries": 1
}
```

3570초는 AI HTTP 대기 3600초와 응답 여유 30초를 맞추는 예시다. 팀 공통 기본값 확정은 별도 합의가 필요하다. 기존 AI 호출은 현재 HTTP 대기에서 30초를 뺀 값을 `deadlineSeconds`에 전달하며, 신규 재시도 옵션은 아직 전달하지 않는다. 서비스에서 자동 사용하려면 AI 설정과 payload에 이 옵션을 연결해야 한다.

## 두 종류의 재시도

### 설치 단계 안에서 다운로드 재시도

연결 끊김, DNS·연결 오류, 알려진 429·503 응답 문구를 확인한다. 같은 검사 작업 폴더와 캐시를 사용하며 2초, 4초, 8초 순서로 기다린다. 대기는 최대 30초이고 단계 상한에 포함된다. 실행 횟수는 남은 시간이 허용하는 범위에서 늘어난다.

패키지·버전 설정 오류와 인증서 신뢰 오류는 즉시 결과를 반환한다. 지원하는 도구의 알려진 오류 문구를 사용하므로 새로운 오류 표현은 추가 확인이 필요하다. Maven·Gradle 빌드 중 다운로드 오류처럼 설치 단계 밖에서 발생한 경우에는 준비 단계 전체 재시도의 조건을 확인한다.

### 준비 단계 전체 재시도

`clone`, `install`, `build`, `test`, `image_build`, `image_load`에서 인프라 오류로 분류된 시간 초과 또는 알려진 일시적인 연결 오류가 대상이다.

- 시간 초과이면 해당 단계와 준비 상한을 각각 두 배로 늘린다. 필드별 최대값은 7200초다.
- 일시적인 연결 오류이면 같은 상한으로 다시 실행한다.
- 전체 상한과 정리 예약 시간은 유지한다. 재시작 전에 91초를 넘는 시간이 남아 있어야 한다.
- 직전 시도의 자원 정리가 완료되어야 한다.
- 첫 시도에서 확인한 커밋 SHA가 있으면 이후 시도에 고정한다. 아직 SHA를 얻지 못한 clone 실패는 원래 ref를 다시 조회한다.
- 앱 검사 실패, 배포 rollout 실패, 장애 후 복구 실패는 기존 결과를 반환한다. AI 수정 패치가 오면 별도 실행으로 처리한다.

재시도는 준비를 처음부터 다시 수행하므로 완료된 빌드 단계도 재실행될 수 있다. 성공한 단계의 산출물을 이어 쓰는 체크포인트 기능은 후속 과제다.

## 요청 중복과 상태 조회

`POST /repositories/validate`는 최종 결과를 기다리는 기존 방식을 유지한다. 완료 결과는 HTTP 200으로 반환한다.

동일한 `requestId`와 동일한 입력이면 완료 결과를 재사용한다. 패치·커밋·검사 설정이 바뀌면 새 실행 ID가 된다. `requestId`가 없으면 서버가 새 값을 부여한다. 새 측정을 의도하면 새 `requestId`를 사용한다.

`GET /executions?requestId=...`로 마지막 실행을 조회할 수 있다. `state`는 `running`, `completed`, `cleanup_pending`이며 실행 중에는 단계와 경과 초도 제공한다. `startedAt`, `updatedAt`은 Unix epoch 초다. `completed`는 결과 저장과 정리가 끝났다는 뜻이며, 성공 여부는 결과의 `observationStatus`와 `exitCode`로 판단한다.

최종 응답의 `source.execution`에 실행 ID, 결과 재사용 여부, 시도별 제한시간·오류 근거·정리 완료 여부, 전체 경과 초를 추가한다. 시간 초과는 기존 `timedOut`, `failurePhase`, `budget`, `validationSupport` 정보를 함께 반환한다. 사용자 앱 복구 결과와 인프라 시간 초과의 기존 분류를 유지한다.

## 중단 후 복구와 운영

SQLite와 복구 목록은 기본 `.runtime/executions`에 저장한다. `CODEREFEREE_EXECUTION_STATE_DIR`로 위치를 바꿀 수 있다. 서비스 재시작 후에도 이 디렉터리가 유지되어야 한다.

자원을 만들기 전에 정확한 이름을 복구 목록에 기록한다. 프로세스가 중단되면 다음 시작 또는 요청 때 해당 컨테이너·볼륨·namespace·관측 namespace·이미지·작업 폴더를 회수한다. namespace 삭제를 확인한 뒤 kind 이미지 회수를 수행한다. 기록이 유실됐거나 정리가 끝나지 않으면 `cleanup_pending`으로 새 작업을 막는다.

중단된 실행은 `sandbox_worker_interrupted` 인프라 오류로 저장한다. 정리 후 같은 요청이 오면 저장된 오류 결과를 반환한다. 재실행하려면 새 요청 ID를 사용한다. 일반 프로세스 오류와 OS 중단에 대비한 경로이며, 호스트 디스크·SQLite 자체의 손상 복구는 별도 운영 과제다.

실행 잠금은 같은 상태 디렉터리를 사용하는 서버 프로세스 사이에 적용된다. 여러 EC2에 걸친 분산 배정은 후속 과제다. 앱 namespace는 호스트 수준 격리를 제공하지 않는다.

## 팀 합의와 후속 과제

- AI HTTP 대기, Sandbox 전체 상한, Backend stale 시간의 일관된 설정
- 신규 옵션의 AI payload 연결과 서비스 기본 활성화 여부
- 재시도의 담당을 Sandbox 준비 단계와 AI 수정 재검증으로 구분하는 계약
- 캐시 결과·실행 이력·복구 목록의 보존 기간과 정리
- 중단된 작업에 대한 사용자 재검증 UX와 상태 표시
- 여러 Sandbox 배정, 멀티레포 그룹 실행, EC2 자동 기동·종료
- 단계별 체크포인트와 실측 이력 기반 소요 시간 안내

첫 레포의 실행 시간을 사전에 정확히 산출하는 기능은 포함하지 않는다. 이번에는 실제 시간 초과에 대응하는 제한된 재시도와 중복·잔여 자원 관리 경로를 제공한다.
