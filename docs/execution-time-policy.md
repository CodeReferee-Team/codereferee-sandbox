# 큰 레포의 실행 시간과 타임아웃 처리 검토

2026-11-04 코드와 10월 19일 설계안 기준이다. 아래 후속 제안은 구현 완료를 의미하지 않는다.

## 현재 구현

- AI 코드의 Sandbox HTTP 기본 제한은 600초다. 현재 Infra의 AI compose 선언은 이를 900초로 덮어쓴다.
  실제 EC2 적용 상태는 별도 확인이 필요하다. BE는 별도 큐·상태 관리 계층이며 이 HTTP 제한을 없애지는 않는다.
- `deadlineSeconds`를 받아 전체 실행 예산을 만들고 정리에 90초를 남긴다. 각 큰 단계는 남은 예산과 단계 상한 중 작은 값을 사용한다.
- 배포 기본 상한 1200초, 개별 시나리오 300초, smoke 180초다. 호출자가 전달한 기한이 더 짧으면 실제 허용 시간도 짧아진다.
- 외부 실행기 시간 초과 시 프로세스 그룹을 종료하고, 어느 단계에서 제한에 걸렸는지 budget·execution_limit에 남긴다.
- 묶음에서 남은 시간이 부족한 실험은 시작하지 않고 미실행 사유를 남긴다. 수행한 실험은 기존 부분 실행 정책으로 처리한다.
- `validationSupport: unsupported_within_budget`는 해당 시간·환경에서 끝내지 못했다는 뜻이다. 그 레포를 영구적으로 지원할 수 없다는 뜻은 아니다.
- 내부 clone/build/rollout 명령들은 독립 제한을 사용한다. 문서의 `--deadline` 내부 전달, GET /status, 비동기 202 작업 API는 아직 없다.
- AI의 busy 재시도 PR #116은 아직 미머지다.

## 실행 전에 정확한 시간을 계산할 수 있나

레포 크기만으로 신뢰할 만한 완료 시간을 계산하기는 어렵다. 같은 소스도 의존성 다운로드, 빌드 캐시,
테스트 외부 의존성, 호스트 사양과 동시 부하 때문에 달라진다. 처음 보는 레포에 정확한 분 단위를 제시하면
오히려 잘못된 안내가 될 수 있다. LLM이 숫자를 만드는 방식을 기본 정책으로 사용하지 않는다.

그렇다고 정해진 시간이 지나면 단순히 지원 불가로 끝내는 것만이 대안은 아니다.

## 권장 방향

### 1. 단계별 실측을 먼저 쌓는다

clone, 의존성 설치, 검사, 이미지 빌드·적재, rollout, 실험, 정리 시간을 나눠 기록한다.
멀티서비스에는 서비스 이름도 함께 남긴다. 레포·설정/의존성 파일 해시·빌더 버전·호스트 사양·캐시 조건이
비슷한 기록이 있을 때만 범위를 안내한다. 표본 수와 근거도 보여준다. 기록이 없으면 첫 실행이라 예상이
어렵다고 안내하고, 실행한 단계부터 안내를 갱신한다.

멀티서비스의 `service_timings`는 이 기반이다. 현재는 기록을 반환할 뿐, 이력 저장소나 예측기는 구현하지 않았다.

### 2. 예상 범위는 안내용으로 사용한다

실측이 쌓이면 중앙값과 상위 구간을 사용해 범위를 안내할 수 있다. 캐시가 없는 첫 실행과 재실행을 구분한다.
모듈 개수·테스트 선언·의존성/이미지 다운로드 필요 여부는 초기 복잡도를 설명하는 보조 근거로 쓸 수 있다.
줄 수나 레포 용량만으로 시간을 확정하거나, 예상이 길다는 이유로 레포를 자동 거절하지 않는다.

Gradle은 실제 실행의 성능 분석 보고서와 캐시 정보를 제공하고, Docker는 레이어·패키지·외부 캐시를 활용한다.
이런 실측과 캐시 조건을 수집하는 것이 사전 추측보다 먼저다.
[Gradle 성능 분석](https://docs.gradle.org/current/userguide/performance.html),
[Docker 캐시 최적화](https://docs.docker.com/build/cache/optimize/).

### 3. 오래 걸리는 작업을 HTTP 연결과 분리한다

큰 레포를 제대로 수용하려면 POST에서 202/jobId를 돌려주고 진행·결과를 조회하는 Sandbox 작업 API가 적절하다.
HTTP 연결이 끊겨도 작업의 실행 기한·취소·결과 보존을 별도로 관리한다. BE/AI와 계약 변경이 필요하다.
이미 BE에 큐가 있다는 것과 AI → Sandbox 실행이 비동기 작업이라는 것은 다르다.

여기에도 실행 시간 상한은 필요하다. 기본/긴 실행 구간, 동시 작업 상한, 사용자 취소, 재시도 정책을 합의한다.
긴 실행을 무제한 허용하거나 로그가 잠시 없다는 이유만으로 실패 처리하지 않는다.

### 4. 기다린 시간을 결과에 반영한다

제한에 도달하면 실패 단계·실제 소요 시간·적용한 제한·실행 완료/미실행 실험을 돌려준다.
“이 레포는 지원 안 함” 대신 “현재 실행 한도 안에 빌드를 마치지 못함”처럼 설명한다.
더 긴 허용 시간이나 다른 사양으로 재실행할 수 있는 조건을 안내한다. 준비 단계 시간 초과를 앱 복원력 FAIL로 바꾸지 않는다.

### 5. 안전한 캐시와 작업 재개를 따로 설계한다

의존성·빌드 캐시를 재사용하면 첫 실행 이후 시간을 줄일 수 있다. 실제 앱 이미지·검사 결과를 재사용하려면
소스·패치·빌드 설정·환경이 같은지 검증해야 한다. 다른 사용자·레포의 실행 결과를 섞으면 안 된다.
현재 요청별 검사 캐시 삭제와 이미지 정리 정책을 바꾸는 작업이므로 별도 범위다.

## 우선순위

### 2026-11-09 추가 후속 과제 — 시간 연장과 재시도

아래는 정책 논의안이며 이번 프론트 지원 구현에 포함하지 않는다.

- 설치·빌드·테스트가 정상 진행 중이었다는 근거와 자원 여유가 있는 시간 초과를 연장 후보로 분류한다. 로그가 잠시 없다는 사실만으로 정지를 판정하지 않는다.
- 일시적인 다운로드 장애는 제한된 재시도를 검토하고, 컴파일 오류·테스트 실패·설정 오류는 수정 후 재검증한다. OOM·디스크 부족은 자원 문제를 먼저 해결한다.
- 기본 10분, 다음 시도 30분, 명시적으로 선택하는 긴 실행 최대 60분은 초기 제안이다. 단계별 적용 범위, 정확한 시간, 재시도 횟수와 모든 시도의 총시간 상한은 AI/Backend 팀과 합의한다.
- 다음 시도의 실행 한도와 현재 시도에 추가하는 시간을 구분한다. 처음부터 재실행하는 방식과 중단 지점 재개를 구분하고 사용자에게 대기 시간·재시도 조건을 안내한다.
- 기존 시도의 실패 단계·부분 결과·실제 소요시간을 보존한다. 재시도 중복 실행과 자원 정리, AI HTTP 제한도 함께 설계한다.
- Chaos 이후 복구 대기 시간은 평가 조건이므로 자동 연장하지 않는다. 다른 제한으로 재검증하더라도 최초 복구 실패를 유지한다.

### 기존 실행 기반의 우선순위

1. 멀티서비스 동작과 진단·정리 실측.
2. 배포 내부 명령까지 동일 기한 전달, 강제 종료 시 잔여 자원 회수와 락 해제 보강. 정리 시간도 서비스 수에 따라 검증.
3. 단계별 시간 이력과 진행 상태 조회. 이 단계에서는 ETA가 없어도 사용자에게 현재 작업을 보여줄 수 있다.
4. AI/BE와 협의해 비동기 작업·취소·긴 실행 정책 도입.
5. 충분한 실측 후 예상 범위와 캐시 최적화. 예상만으로 사전 거절하는 정책은 권하지 않는다.

이 순서는 교수님 질문에 “미리 정확히 맞힌다”는 약속 대신, 처음 실행은 근거가 부족함을 알리고
실행 기록으로 안내를 개선하며 큰 레포도 별도 작업 수명주기로 처리하겠다는 답을 제공한다.
