요청별 validation.yaml 업로드

사용자 레포에 설정 파일을 commit/push하지 않고 이번 검사의 임시 clone에만 설정을 적용합니다. 설정을 업로드하지 않은 기존 요청은 기존 자동 탐색·레포 설정 경로를 유지합니다.

요청 전달

  • Frontend → Backend: 기존 JSON 요청에 선택 문자열 필드 validation_yaml을 추가합니다. multipart나 파일 경로를 전송하지 않습니다.
  • Backend → Redis → AI: 큐의 선택 필드 validationYaml로 전달합니다. AI의 요청 상태에도 문자열을 보존해 첫 실행과 모든 재검증에서 동일하게 전송합니다.
  • AI → Sandbox: POST /repositories/validate의 validationYaml입니다. SDK는 업로드 설정의 해시를 결과에서 확인하며, 이를 무시한 구버전 Sandbox의 성공 결과를 그대로 신뢰하지 않습니다.
{
  "repositoryUrl": "https://github.com/example/app",
  "requestId": "request-upload-example",
  "validationYaml": "version: 1\nservice:\n  port: 8000\n"
}

위 설정의 Dockerfile·서비스 경로·포트 등은 실제 레포에 맞아야 합니다. 경로·스택 자동 탐색과 설정 스키마 검사는 기존 실행 계획 해석기가 담당합니다.

적용 순서

  1. 요청한 레포와 커밋을 clone합니다.
  2. 업로드 설정을 .codereferee/validation.yaml에 기록합니다. 레포에 같은 파일이 있어도 이번 요청에서는 업로드를 우선합니다.
  3. Refiner 패치가 있다면 그 위에 적용합니다. 따라서 설정을 고친 패치가 업로드 원본에 의해 덮이지 않습니다.
  4. 기존 설치·빌드·배포·관측을 수행하고 기존 수명주기로 작업 디렉터리·namespace·요청 이미지를 정리합니다.

GitHub에는 push하지 않으며 원본 커밋 SHA도 바꾸지 않습니다. Refiner의 소스 문맥 역시 같은 업로드 설정을 먼저 적용한 뒤 누적 패치를 적용해 읽습니다. 수정 대상이 추가 레포라면 main의 설정 파일을 해당 레포에 잘못 쓰지 않습니다.

제한과 안전장치

  • 최대 64KiB UTF-8 텍스트이며 BOM·CRLF/CR은 LF로 정규화합니다. 비어 있거나 NUL을 포함한 파일, 불완전한 조각, version 1/2/3가 아닌 파일을 거절합니다.
  • 안전한 YAML 로더를 사용하고 업로드 YAML alias·재귀·지나친 깊이/복잡도를 거절합니다. 일반적인 문자열 키와 스칼라·목록·매핑을 사용하세요.
  • 사용자 파일명·경로는 서버 저장 경로로 사용하지 않습니다. 임시 전달 파일은 UUID 이름이며, clone 내 설정 경로도 symlink와 경로 이탈을 거절합니다.
  • 배포 프로필·fixture·미리 배포된 target과 업로드를 동시에 지정하지 않습니다. 모호한 우선순위를 만들지 않고 거절합니다.
  • SQL 초기화 파일이나 Dockerfile까지 함께 업로드하는 기능은 아닙니다. YAML이 참조하는 파일은 선택한 레포 커밋에 있어야 합니다. version 3의 설정 및 초기화 파일 기준 레포는 main입니다.
  • Local Docker fallback은 이 업로드 계약을 지원하지 않습니다. 외부 Sandbox가 없으면 설정을 조용히 버리지 않고 판정 불가로 반환합니다.
  • 운영 비밀번호·API 키를 넣지 말고 재현용 값과 임시 DB 템플릿을 사용하세요. 설정은 요청 처리와 재검증에 사용되며, AI 작업 상태에 보관될 수 있습니다.

결과 확인

source.configuration_input에 source: request_upload, 고정 경로, 정규화한 업로드의 uploaded_sha256·바이트 수, 패치 적용 후의 effective_sha256를 기록합니다. 서로 다르면 Refiner 패치 등으로 실제 사용 설정이 바뀐 것입니다. 보고서에 업로드 설정 전문을 복제하지 않습니다.

배포 순서

Sandbox → AI → Backend → Frontend 순서로 배포하고 기존 요청이 진행 중인지 먼저 확인합니다. Frontend는 Backend의 GET /api/validations/capabilities가 업로드 지원을 밝힌 경우 파일 입력을 활성화합니다. 같은 요청을 진행 중인 Worker·Sandbox를 강제로 재시작하지 마세요.

PostGIS·초기화 SQL 사용에는 해당 DB 재현 지원도 함께 필요합니다. 업로드 연결만 배포한다고 임의의 DB·확장·외부 API까지 자동 지원되는 것은 아닙니다.
