# 멀티서비스 확장 백로그

## 2026-11-13 상태 정정

아래 표에는 최초 작성 시점의 제안이 남아 있다. 다음 항목을 미구현으로 다시 집계하지 않는다.

- 설정 기반 브라우저 업무 검사: [구현 및 검증 범위](browser-business-validation.md).
- 단계별 제한·전체 시간 예산·준비 재시도: [실제 검증](execution-timeouts-retries-results.md).
- 설정 기반 멀티레포 서비스 그룹: [전체 큐 연동을 포함한 검증](multi-repository-validation-results.md).
- 추가 레포 패치 계약과 순차 대상 전환: [패치 계약](multi-repository-patches.md). 이번 작업의 실제 검증 결과와 LLM 대역 사용 여부는 별도 기록한다.

외부 프로젝트 사례 확대, 독립 업무의 병행 관측, 복잡한 인증, 자동 탐색과 전용 Worker·EC2 온디맨드는 별도 후속 범위다.
표의 기존 항목은 해당 기능의 최초 요구와 남은 고도화 맥락으로 읽는다.

특정 레포의 업무 로직을 Sandbox에 구현하지 않는다. 레포 독립적인 실행·관측 계약을 제공하고 실제 레포는 검증 사례로 사용한다. 아래는 이번 PR 본문에도 옮길 후속 과제다. 계획을 구현 완료로 표시하지 않는다.

## 이번 단계의 완료 조건

- 명시적 설정으로 앱 5개와 요청 전용 DB를 준비하고 중간 실패 시 진단·정리한다.
- 루트 빌드/테스트를 한 번 수행하며 검사 DB와 배포 DB를 분리한다.
- 인증 setup/토큰 추출/응답 내용 확인을 장애·부하 probe에 공통 연결한다.
- 정상 업무 baseline 뒤에만 실험하고 복구와 실행 근거를 확보한다.
- 제품 기본 timeout 유지, 실측용 확장 인자 기록, 자원 회수와 기존 경로 회귀 확인.
- 실제 통과/실패/미실행 범위를 결과 문서와 PR에서 구분한다.

## 후속 우선순위

| 우선순위 | 항목 | 필요한 이유 / 완료 조건 |
| --- | --- | --- |
| P1 | 서비스별 독립 업무 probe 병행 관측 | 한 서비스 장애가 의존/비의존 업무에 미치는 영향을 비교한다. 서비스별 성공률·지연·복구와 미실행 경로를 별도 반환한다. 현재 순차 steps와 peer Pod 진단으로 대체하지 않는다. |
| P1 | 프론트 브라우저 업무 검증 | Vite 정적 빌드·서빙과 선택한 HTTP 장애·부하는 구현·실측했다. 다음 단계로 브라우저 JavaScript 실행, UI 동작, 클라이언트 라우팅, API/CORS와 인증·외부 의존성을 검증한다. [현재 지원 범위](frontend-static-validation.md)를 전체 브라우저 E2E로 확대 해석하지 않는다. |
| P1 | 로컬 디스크 보호 | Windows에서 Docker의 Linux 데이터 경로를 호스트에서 측정하지 못하는 경우와 직접 CLI가 API 사전 점검을 거치지 않는 경우를 보강한다. 빌드 전·실행 중 호스트/실행기 공간과 동시 빌드 예산을 확인하고, 공간 부족을 앱 결함으로 반환하지 않는다. 기존 DB·다른 프로젝트 데이터의 자동 삭제 없이 요청 자원과 명시한 재생성 가능 캐시만 회수한다. |
| P1 | 외부 의존성·초기 데이터 선언 계약 | 임의 레포의 테스트 결제·검색 엔진·모델·데이터를 재현한다. 지원 타입·버전·초기화·자원 상한·정리를 명시하고 운영 비밀값을 사용하지 않는다. 특정 사례의 결제/추천 코드 구현이 아니다. |
| P1 | 대형 레포의 운영 시간 예산 | 빌드/테스트/배포/실험의 실제 소요시간과 timeout 위치를 구분한다. 검증용 시간 확장을 제품 기본값 변경으로 혼동하지 않는다. 연산량 ETA는 확약하지 않고 비동기 실행·운영자 예산 설정 계약을 검토한다. API 외부 단계 기한뿐 아니라 직접 CLI/진단 실행의 kind 이미지 적재 등 하위 도구에도 기한·자식 프로세스 정리를 일관되게 적용한다. |
| P1 | 시간 연장·재시도 정책 합의 | 미구현 후속 과제다. 설치·빌드·테스트의 진행 근거와 자원 여유가 확인된 시간 초과, 일시적인 다운로드 장애, 설정/코드 오류, 자원 부족을 구분한다. 재시도별 한도·횟수·전체 누적 시간과 사용자 동의, AI HTTP 제한을 함께 정한다. 기본 10분 → 재시도 30분 → 긴 실행 최대 60분은 초기 논의안이며 확정값이 아니다. 처음부터 재실행하는 시간과 중단 지점 재개를 구분하고, 기존 실패·부분 결과를 보존한다. Chaos 복구 제한은 평가 조건이므로 자동 연장하지 않는다. |
| P1 | Gradle 집계 루트의 모호한 자동 배포 감지 | 실행 앱이 여러 개인데 루트 단일 build/libs jar를 가정하는 오판을 막는다. 명시적 v2 설정을 안내하고 단일 앱 관습 탐색 회귀를 확인한다. |
| P2 | 멀티서비스 자동 탐색 | 여러 앱의 존재와 후보는 제시하되 포트·의존성·업무 진입점·장애 대상을 임의 확정하지 않는다. 모호하면 설정이 필요함을 구조화해 안내한다. |
| P2 | 준비 실패와 재시도 계약 | 실제 레포에서 장애 복구 직후 새 인증 setup이 503인 사례를 보존했다. 명시적인 준비 요청 timeout 분리는 구현했다. 계정 생성의 멱등성·gateway 준비 상태·재시도 가능 오류·횟수/총시간 상한을 정하고, 장애 후 복구 실패를 임의 재시도로 성공 처리하지 않는다. |
| P2 | 준비 시간 단축 | 실측 단계별 시간을 근거로 이미지 적재 재사용과 의존 관계가 없는 앱의 동시 기동을 검토한다. 메모리/CPU 시작 피크, 중간 실패 진단·정리와 dependsOn 의미를 유지하며 현재 순차 배포를 근거 없이 병렬로 바꾸지 않는다. |
| P2 | 인증 만료·복잡한 세션 수명주기 | 현재 observer/부하 Pod별 setup과 공유 인증 세션 범위를 명시한다. 장시간 검사, 사용자별 로그인, refresh/쿠키 인증은 명시적 계약과 만료 실패 분류를 마련한다. |
| P2 | 조건 변경 재검증 정책 | 부하/메모리/코드 중 한 조건씩 변경하고 횟수·총시간 상한을 정한다. 단순 OOM만으로 누수나 용량 부족을 단정하지 않는다. AI/Backend 팀과 정책을 합의한다. |
| P1 | 지연 정리의 재회수 | namespace가 정리 대기 상한 뒤에 삭제돼 이미지가 남는 경우, 요청 ID 기준 재확인·회수를 수행한다. 현재 실패 기록과 namespace 삭제 전 노드 이미지 삭제 금지 정책은 유지한다. 강제 finalizer 제거/전역 prune으로 대체하지 않는다. |
| P2 | 멀티레포 서비스 그룹 | repo별 commit·빌드·서비스 매핑과 실패 원인을 보존하고 그룹 자원을 회수한다. 단일 레포 앱 5개 지원과 구분한다. |
| P2 | Sandbox EC2 요청 배정·온디맨드 | 동시 요청의 임대/준비 확인/상한/고아 회수와 자동 기동·종료를 구현한다. 한 요청의 다중 인스턴스 배치와 여러 요청의 분산 배정을 구분한다. AWS 실측은 별도 승인 범위다. |

## PR 작성 시 필수 구분

1. 구현한 공통 기능과 로컬 실측용 레포 설정을 구분한다.
2. 배포한 앱 수와 실제 관측한 업무 경로를 따로 적는다. 앱 5개 기동을 모든 업무 기능 합격으로 표현하지 않는다.
3. 장애 대상·probe 진입점·실제 DB 요청·부하 단계를 명시한다.
4. 테스트 실패, 인프라 실패, 제외 기능과 미실행 환경을 숨기지 않는다.
5. 위 후속 과제는 이번 PR에서 완성했다고 주장하지 않는다. 원격 push/PR은 사용자 확인 후 진행한다.
