# FE·API·DB 검증 기록

2026-11-09 최초 실측 후 2026-11-11 최종 코드로 다시 확인했다. Windows + Docker Desktop + 기존 kind-codereferee에서 전용 fixture의 로컬 Git 미러를 사용했다. 프로세스 한정 Git URL 재작성과 FastAPI TestClient로 `/repositories/validate`를 호출해 검사·빌드·배포·관측·정리를 실행했다.

## 구성과 업무

- Vite 정적 FE와 FastAPI, 요청 전용 PostgreSQL을 사용했다.
- FE의 `/api/` 요청을 선언한 API Service로 전달했다.
- Chromium에서 입력·저장·HTTP 201 및 JSON 확인·화면 내용 확인·새로고침 후 재조회까지 6단계를 실행했다.
- 별도로 PostgreSQL의 저장 행 개수를 읽어 UI 저장이 실제 DB에 반영되는지 확인했다.
- 장애 중에는 FE를 경유해 저장된 데이터를 조회하는 HTTP 업무를 반복 측정했다.
- 단일 replica, FE 500m·128Mi, API 1000m·256Mi 설정이다.

## 실제 실행 결과

첫 일반 실행에서 브라우저 6단계를 배포 후와 HTTP 검사 후 각각 통과했다. `observed / exitCode 0 / browserLoaded true`였으며 namespace와 두 앱 이미지를 호스트·kind에서 모두 삭제했다. 해당 실행에서 부가 SQL 수집 스크립트가 잘못된 Python 모듈을 감싸 행 수집이 빠졌다. 보조 스크립트를 수정한 뒤 아래 실행에서 DB를 직접 확인했다.

### 최종 코드의 부하·장애 연속 실행

2026-11-11 실행은 약 15분 26초가 걸렸다. 브라우저 업무 전체 시간 제한을 적용한 커밋 `c2adf5e` 기준이다.

| 검사 | 관측 상태 / 종료 코드 | HTTP 복구 시간 | 실패 / 전체 HTTP 관측 | 완료 후 UI 저장 행 |
| --- | --- | --- | --- | --- |
| 초기 브라우저 업무 | observed / 0 | 해당 없음 | 해당 없음 | 1 |
| 동시 사용자 부하 | observed / 0 | 0초 | 전후 확인 0 / 10 | 2 |
| API Container Kill | observed / 0 | 6.16초 | 2 / 62 | 3 |
| API Service 라우팅 단절 | observed / 0 | 12.18초 | 16 / 31 | 4 |
| PostgreSQL 통신 단절 | observed / 0 | 15.55초 | 5 / 27 | 5 |

모든 장애 후 새 브라우저 세션에서 6단계를 다시 통과했다. DB 업무 조회용 행도 유지됐다. API 컨테이너 종료 전후 container ID 변경과 restartCount 증가를 확인했다. DB 장애는 PostgreSQL Pod에 100% 패킷 손실을 주입했고 실제 업무 실패 후 복구를 관측했다. namespace, 호스트 및 kind의 두 앱 이미지, 검사 캐시와 작업 폴더 정리 결과에 오류가 없었다.

`measurement_valid: true`, 요청한 `target_users: 5`는 충족했다. 50명 단계부터 HTTP 5xx가 발생했고 100·200명 단계에서는 시간 초과도 발생했다. 부하가 끝난 뒤 업무와 DB 조회가 복구됐다. 200명 단계의 실패율 93.35%를 결과에 보존했다. 원인 확정과 자원 변경 후 비교 실험은 후속 과제다.

## 실행 환경에서 발견한 사항

- 기본 seccomp 설정에서 Chromium 자체 격리를 사용할 수 없어 기동이 실패했다. 공식 프로필을 설치한 뒤 격리를 켠 실제 Chromium 실행을 확인했다.
- Windows에서 Bash 테스트 11건이 경로·CRLF 조건 때문에 실패했다. Windows 적용 대상과 Linux POSIX 실행을 분리해 확인했다.
- Linux 첫 실행의 읽기 전용 테스트 소스에서 `.runtime` 작성 오류 8건이 발생했다. 컨테이너 임시 복사본에서 다시 실행했다.
- 1 CPU 조건에서 기존 1초 프로세스 시작 검사가 PID 파일 생성 전에 시간 초과됐다. 기록을 보존하고 기존 2 CPU 조건에서 전체 331개 통과를 확인했다.
- 2026-11-09 최종 Windows 실행에서 API import 검사가 15초를 넘긴 기록을 보존했다. 2026-11-11 재실행에서는 Windows 적용 대상 322개 중 321개가 통과했고 1개는 플랫폼 조건으로 제외됐다. POSIX bootstrap 12개는 Linux 전체 테스트에 포함한다.

## 추가 확인

- `/api/`를 제거해 API의 `/items`로 전달하는 구성에서도 브라우저 6단계와 실제 SQL 저장 확인을 통과했다. 이 구성에서는 장애 대상을 FE로 바꿔 Container Kill 전후 업무 재검증과 정리를 확인했다.
- 잘못된 마지막 화면 확인 조건을 선언한 실행은 6단계 중 5단계 완료 후 `browser_action_timeout`, `observed / exitCode 1`로 끝났다. 단계별 제한 15초보다 짧은 업무 전체 제한 5초를 적용했다. 브라우저 프로세스 시작과 종료를 포함한 보고 소요 시간은 약 8초였다. 장애는 주입하지 않았고 namespace·호스트·kind 앱 이미지를 회수했다.
- 생성된 FE 이미지를 프록시 ConfigMap 없이 `nginx -t`로 확인해 단독 정적 FE의 설정도 유효한 것을 확인했다.
- 실제 JSON을 기존 AI 파서와 결정적 Judge에 전달했다. 정상·장애 후 복구는 Pass, 브라우저 업무 실패는 Fail이었다. 실제 HTTP 복구 결과와 실제 브라우저 실패를 결합한 별도 계약 검사도 Fail이었다. 이 결합 검사는 장애 후 브라우저 실패를 새로 주입한 실측과 구분한다.
- AI의 기존 비정상 종료 설명이 브라우저 업무 실패를 build 실패로 표현하는 현상을 확인했다. Sandbox 실패 단계와 브라우저 근거는 보존되며, 설명 구분은 AI 측 후속 작업이다. 호환 확인에는 기존 파서와 결정적 판정 함수를 사용했다.

## 최종 회귀와 정리 확인

2026-11-11 실행 결과다.

- Windows 적용 대상 322개 중 321개 통과, 1개 플랫폼 조건 제외.
- 제외된 1개는 레포 폴더의 쓰기 권한 부족을 인프라 오류로 분류하는 POSIX 권한 회귀 테스트다. Linux 전체 334개 실행에 포함돼 통과했다.
- Linux 전체 334개 통과. POSIX bootstrap 12개도 포함한다.
- 기존 HTTP 전용 실행은 `observed / exitCode 0`, AI 파서의 `browser_check_attempted: false`와 결정적 판정 Pass를 확인했다.
- 브라우저 런타임 준비 명령의 실제 이미지 빌드 재사용·kind 적재·seccomp 프로필 설치를 확인했다.
- 6개 실제 요청을 대상으로 namespace, 호스트·kind 요청 이미지, 검사 볼륨, 작업 폴더, 임시 컨테이너와 브라우저 Pod 잔존을 독립 조회했다. 모든 잔존 목록이 비어 있었다.
- 재사용하는 브라우저 런타임 이미지와 기존 서비스 컨테이너를 확인했다. 점검 시 C 드라이브 여유는 약 7.3 GiB였다.

## 범위

실측 환경은 Windows의 Sandbox 내부 컨테이너·Kubernetes·브라우저·DB다. AI 파서·결정적 판정 호환도 로컬에서 확인했다. 후속 실측 대상은 Backend·Redis·AI 전체 경로, LLM 자동 수정 생성, AWS 배포와 Mac 실행이다.

브라우저는 장애 전후에 실행하며 장애 중에는 HTTP 업무를 측정한다. 새 FE fixture의 실측 시나리오는 위 네 가지와 별도 구성의 FE Container Kill이다. 기존 13종 기능은 전체 회귀 테스트에서도 확인한다. UI 연속 복구 측정과 브라우저 동시 사용자 부하는 후속 과제다.

원본 JSON·로그는 로컬 `tmp/browser-business-20261109`와 `tmp/browser-business-20261111`에 보존한다. 커밋에는 재현용 소스·설정과 이 요약을 포함한다.
