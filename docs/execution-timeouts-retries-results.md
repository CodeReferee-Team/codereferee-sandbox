# 시간 제한·재시도 검증 기록

2026-11-11 Windows·Docker Desktop·기존 kind-codereferee에서 수행했다. Sandbox HTTP API는 TestClient로 호출했고 실제 Git 복제, Docker 검사와 빌드, kind 배포, HTTP 확인을 실행했다. 작은 Python 레포와 제어 가능한 의존성 다운로드 서버를 사용했다.

## 실제 실행

| 케이스 | 주입한 조건 | 확인 결과 |
| --- | --- | --- |
| 다운로드 단계 내 재시도 | 처음 두 다운로드 연결을 끊음 | 설치 3번째 호출 성공, 대기 2초·4초, 한 번의 준비 시도에서 배포 성공 |
| 준비 전체 재시도 | 첫 다운로드 연결을 끊고 단계 내 재시도는 끔 | 인프라 오류 후 정리, 같은 제한시간으로 두 번째 준비 성공 |
| 단계 시간 연장 | 첫 다운로드 응답을 60초 지연 | 설치 12초 시간 초과, 자원 정리 후 24초로 재시도해 배포 성공 |
| 배포 준비 시간 초과 | 앱의 HTTP 기동을 늦추고 rollout 상한을 5초로 지정 | 인프라 오류·timedOut 반환, 추가 재시도 없이 자원 정리 |
| 누적 시간 부족 | 전체 105초·정리 예약 90초, 다운로드 응답 지연 | 설치 중 시간 초과, 남은 전체 시간이 부족해 추가 재시도 차단, 자원 정리 |
| 프로세스 강제 종료 | 실제 자원을 만든 프로세스 트리를 강제 시간 초과시킴 | 잠금 해제, 새 복구 실행에서 `sandbox_worker_interrupted` 저장, 정확한 요청 자원 회수 |

API 실측 5건 모두 실행 중 중복 POST의 HTTP 409와 완료 후 같은 POST의 저장 결과 재사용을 확인했다. 준비 전체 재시도에서는 시도별 resource ID가 바뀌고 커밋 SHA가 유지됐다. 최종 정상 응답은 `observed / exitCode 0`, 시간 초과 응답은 `infrastructure_error / exitCode null`이었다.

첫 연장 실측은 5초에서 10초로 늘렸지만 두 번 모두 설치 시간 초과였다. 초기 제한이 짧아 첫 시도의 지연 다운로드가 시작되기 전에 설치 프로세스가 중단될 수 있었다. 이 결과는 실패 기록으로 보존했고, 요청이 실제 다운로드에 진입한 것을 확인하는 12초→24초 조건으로 별도 재실행했다.

## 강제 종료와 정리

제어된 강제 종료 검증에서는 요청 namespace, 관측 namespace, 호스트·kind 이미지, 실행 중 검사 컨테이너, 검사 볼륨, 작업 폴더를 만들었다. 프로세스 트리 종료 후 별도 복구 경로로 모두 회수했다. 자식 프로세스 종료와 반복 복구의 멱등성도 확인했다.

별도 조회로 실패 기록을 포함한 resource ID 10개를 감사했다. 요청 namespace·관측 namespace·검사 컨테이너·검사 볼륨·호스트/kind 이미지·작업 폴더가 남지 않았다. 공유 클러스터, 운영 관측 컨테이너, 기존 DB와 다른 프로젝트 컨테이너는 유지했다.

## 회귀와 연동 범위

최종 Windows 회귀는 346개 중 345개 통과, 쓰기 권한을 강제로 제한하는 플랫폼 조건 테스트 1개 제외다. Linux는 해당 테스트와 POSIX 부트스트랩 테스트를 포함해 358개 전부 통과했다. Windows 실행 목록에서 POSIX 부트스트랩 12개를 제외하고 Linux에서 실행했다.

실제 결과 5건을 현재 AI 응답 파서로 읽어 상태·exit code·시간 초과·인프라 오류·시도 이력이 유지되는 것을 확인했다. AI 모델·Judge 코드는 변경하지 않았다.

이번 실측은 Sandbox API 내부 경로다. Backend·Redis·AI 전체 신규 재시도 실행, 새 AWS 호스트, Mac 실측은 추가 확인 범위다. 신규 옵션을 AI 요청에 연결하는 작업과 공통 시간 상한은 팀 합의가 필요하다. 모든 Chaos를 재실행한 세션은 아니며 기존 시나리오는 회귀 테스트로 확인했다.
