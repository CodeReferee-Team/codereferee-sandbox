# Vite 정적 프론트 실행과 검증

## 실행 방식

기존 Node 자동 실행은 `start` 또는 `dev`를 실행하고 기본 포트 3000을 사용했다. Vite 개발 서버는 이 포트 설정만으로 Kubernetes에서 정상 서비스되지 않았다.

아래 조건에 해당하는 앱은 빌드 결과를 비권한 Nginx로 제공한다.

- 실행 대상 디렉터리에 `package.json`, `index.html`, Vite 의존성이 있다.
- `build` 스크립트의 마지막 명령이 `vite build`다. `tsc -b && vite build`도 해당한다.
- 선언된 `start` 또는 `dev` 진입점이 Vite CLI이거나 별도 실행 진입점이 없다.

독립 Node 서버를 선언한 `start`/`dev`와 명시적 Dockerfile의 기존 실행 경로를 유지한다. SSR·라이브러리·별도 서버가 필요한 앱은 실행 계약에 맞는 Dockerfile을 제공해야 한다.

검사 컨테이너에서 설치·빌드·선언된 테스트를 실행한 뒤, 이미지 빌드 단계에서 정적 배포 산출물을 만든다. 최종 이미지에는 정적 파일과 웹서버를 넣는다. Vite 설정은 이미지 빌더 안에서 읽으며 Sandbox 호스트에서 실행하지 않는다.

## 지원 설정

| 항목 | 동작 |
| --- | --- |
| 패키지 매니저 | npm 또는 `packageManager`에 정확한 버전을 선언한 pnpm. 잠금 파일이 있으면 `npm ci` / `pnpm install --frozen-lockfile` 사용 |
| 설치와 실행 | 검사와 이미지 빌드가 같은 패키지 매니저 명령을 사용 |
| Node | 기존 `.nvmrc` / `.node-version` / `engines.node` 선언 우선. 선언이 없는 Vite 앱의 기본 주 버전은 22 |
| 서빙 포트 | 기본 8080. 생성된 정적 서버는 1024~65535의 명시적 포트 지원 |
| 사용자 | 최종 웹서버 UID/GID 101. 런타임 이미지의 digest 고정 |
| 빌드 옵션 | `--outDir`, `--base`, `--mode`의 리터럴 값. 셸 변수로 결정하는 인자는 명시적 Dockerfile 필요 |
| 출력 폴더 | Vite가 해석한 실제 `outDir`. 빌드 컨텍스트 내부의 별도 폴더와 `index.html` 필요. 컨텍스트 밖 경로와 산출물 심볼릭 링크 거부 |
| 배포 경로 | `/` 또는 `/demo/`처럼 영문·숫자·밑줄·하이픈으로 구성되고 `/`로 끝나는 로컬 절대 경로. 외부 CDN/상대 경로는 자동 구성 범위 밖 |
| SPA 경로 | 앱 경로의 새로고침은 `index.html` 반환. 존재하지 않는 JS·CSS 등 파일은 404 |
| 리다이렉트 | 상대 경로 사용. 외부 접속 포트와 컨테이너 포트가 달라도 내부 포트로 이동시키지 않음 |

빌드 결과를 정적으로 서빙할 수 없다고 확인한 경우 `ConfigurationRequired`로 전달한다. 빌드 자체가 실패한 경우의 오류와 이 설정 요구를 구분한다.

지원 범위의 기본 앱은 URL만 입력할 수 있다. 복제본이나 포트를 지정할 경우 기존 설정을 사용한다.

```yaml
# .codereferee/validation.yaml
version: 1
service:
  port: 8080
  healthPath: /
  replicas: 2
```

기본값을 쓰면서 복제본만 바꾸려면 `service: {replicas: 2}`로 선언할 수도 있다. 버전 2 멀티서비스의 프론트 서비스에도 생성된 포트·health 기본값이 반영된다.

pnpm 레포의 선언 예시는 다음과 같다.

```json
{"packageManager": "pnpm@10.33.0"}
```

잠금 파일만 있고 사용할 패키지 매니저의 버전을 결정할 수 없거나 잠금 파일이 충돌하면 설정을 요구한다. 복잡한 배포 계약은 Dockerfile로 명시한다. Yarn·Bun 등 다른 매니저의 설치·검사는 추가 실행기 지원이 필요하며 Dockerfile만으로 검사 단계가 바뀌지는 않는다.

## 실제 검증 결과

2026-11-06 실행과 2026-11-09 추가 경계 검증을 구분한다. Windows + Docker Desktop + kind 환경이다.

| 대상 | 설치·빌드·검사 | 실행 검증 |
| --- | --- | --- |
| CodeReferee React/Vite 프론트, `399b7a4775f33ce600348e6a960d9cb906e83d00` | 설치·빌드 및 원본 테스트 43개 통과 | Container Kill·네트워크 지연·라우팅 단절·부하 |
| 외부 Vue/Vite RealWorld, `741c215ef0f674f90fcb03c5493a1b3a3a7f1b03` | pnpm 10.33.0 설치·빌드 및 명시한 `test:unit` 통과 | 복제본 2개 중 Pod 1개 삭제·부하 |

두 레포 모두 실제 clone → 격리된 검사 → 이미지 빌드 → kind 배포 후 실행했다. HTML 200, JS/CSS의 올바른 MIME과 파일 내용, SPA 경로의 HTML 반환, 없는 JS/CSS 404를 확인했다. 장애·부하 스크립트는 클러스터 내부에서 Service를 거쳐 HTTP를 관측한다. 파일 응답 검사는 별도 port-forward로 확인했다.

| 대상 / 모드 | 결과 | 실패 HTTP / 전체 관측 표본 | 복구 초 |
| --- | --- | --- | --- |
| React / Container Kill | observed / 0 | 1 / 51 | 2.44 |
| React / Network Latency | observed / 0 | 0 / 24 | 0.0 |
| React / Service Routing | observed / 0 | 9 / 19 | 5.71 |
| Vue / Pod Delete, 1 of 2 | observed / 0 | 0 / 42 | 0.0 |

네트워크 지연 실행의 p95는 603.81ms였다. 복구 0초는 HTTP 중단을 표본에서 포착하지 않았다는 의미다. 양쪽 부하는 1·5·10명 각 5초, 5·25·50개 요청이 모두 HTTP 200이었고 `measurement_valid=true`였다. 이는 정적 파일 HTTP 검증이며 브라우저를 실행한 사용자 행동 부하와 구분한다.

두 요청 모두 장애 뒤 파일 응답을 다시 확인하고 namespace·host/kind 이미지·작업 폴더 회수를 확인했다.

### 추가 경계 검증

- 실제 Vite 빌드로 `--outDir output/web --base=/demo/`를 적용하고 Nginx에서 HTML·JS·CSS, SPA 경로, 누락 파일 404와 외부 경로 404를 확인했다.
- 최초 보조 코드의 준비 실패가 `NameError`로 가려졌다. 준비 실패 처리를 수정하고 실제 헤더를 확인한 결과, Nginx가 외부 접속 포트 대신 8080으로 리다이렉트하는 문제를 발견했다. 상대 리다이렉트로 수정한 뒤 같은 조건이 통과했다. 실패 기록도 보존했다.
- 실제 Vite 설정 해석과 산출물 내보내기를 컨테이너에서 실행해 SSR, 라이브러리, 외부 CDN base, 컨텍스트 밖 출력, 심볼릭 링크를 거부하는 것을 확인했다. 이 거부 검사는 제어된 구성으로 수행했다.
- 별도 실제 Docker 빌드에서 유효한 라이브러리 산출물의 정적 배포는 설정 요구로, JavaScript 문법 오류는 일반 빌드 실패로 구분했다. HTML 진입점을 만들지 않는 구성도 설정 요구로 처리했다. 제어용 라이브러리의 초기 패키지명 누락으로 발생한 빌드 실패는 별도 기록으로 보존했다.
- Windows JSON 출력은 기본 콘솔 인코딩에서 빌드 로그의 Unicode 때문에 실패했다. ASCII escape를 사용하는 JSON으로 수정하고 cp949 회귀 테스트를 추가했다.
- 최종 Windows 회귀 307개 중 306개 통과, POSIX 권한 1개 제외. Linux 전체 319개 통과이며 Bash와 같은 권한 검사를 포함한다.
- Linux 재실행 중 기존 1초 타임아웃 테스트에서 자식 프로세스의 PID 파일 미생성 오류가 한 번 있었다. 해당 로그를 보존하고 다른 빌드가 없는 환경에서 전체 319개가 통과하는 것을 다시 확인했다. 테스트 준비 순서의 안정화는 별도 후속 과제다.

## 검증 한계와 후속 과제

- 외부 Vue의 원본 테스트는 브라우저 E2E도 포함한다. 이번 로컬 검증 설정은 `test:unit`만 명시했으며 원본 전체 테스트 통과로 표시하지 않는다.
- 버튼 클릭·로그인 UI·클라이언트 JavaScript 실행·API/CORS·외부 서비스 연동은 별도 브라우저 업무 검증 범위다. HTTP SPA fallback만으로 클라이언트 라우터의 동작을 판정하지 않는다.
- 이번 프론트 실측은 위의 선택한 장애·부하다. 13종 전체 시나리오, Backend/Redis/AI 전체 연동, LLM 수정 생성과 AWS/Mac 실측을 추가 수행한 결과는 아니다.
- 최초 Node 20 실행은 국제화 데이터 차이로 원본 테스트 42/43이었다. 이후 기본 Node 22에서 43개가 통과했다. 실패를 숨기거나 테스트를 제거하지 않았다.
- 디스크 고갈로 중단된 실행을 성공으로 세지 않았다. 해당 요청 namespace 부재, 임시 볼륨과 요청 이미지 회수를 확인하고 새 요청으로 실제 레포 검증을 완료했다. 기존 DB와 다른 프로젝트 데이터는 정리 대상에서 제외했다.
- Windows Docker 데이터 경로 측정, 직접 CLI의 디스크 점검과 실행 중 공간 감시는 별도 보강 과제다. 이번 보조 실행은 빌드 전 여유 확인과 순차 실행을 사용했다.
- 캐시 최적화, 브라우저 검증, 시간 연장·재시도 정책은 [백로그](multi-service-backlog.md)와 [실행 시간 정책](execution-time-policy.md)을 따른다.

원본 JSON·실패 로그·제어용 설정은 로컬 `tmp/frontend-validation-20261106`에 보존한다.
